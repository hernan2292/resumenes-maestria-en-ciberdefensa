  • Concurrencia Avanzada en Go (Goroutines, Channels, Mutex)
    🏭 Caso de Uso Práctico en Producción
    Procesamiento en paralelo de lotes de pagos o scrapers concurrentes. Por ejemplo, llamar a 5 pasarelas de pago externas simultáneamente (Stripe, PayPal, MercadoPago) esperando la respuesta más rápida o consolidando resultados antes de un timeout global.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "En Go la concurrencia no usa hilos del SO por petición, sino el scheduler M:N del runtime. Las goroutines pesan solo ~2KB inicialmente. Aplico el principio CSP: 'No comuniques compartiendo memoria, comparte memoria comunicándote' mediante canales. Cuando requiero exclusión mutua en estructuras compartidas utilizo sync.RWMutex o operaciones atómicas para evitar contention overhead."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Qué pasa si envías datos a un canal cerrado? Lanza un panic fatal inmediatamente.
    • ¿Y si lees de un canal cerrado? Devuelve el valor cero del tipo y ok = false sin bloquear.
    • ¿Cómo evitas Goroutine Leaks? Pasando un context.Context con timeout o canal de cancelación para que la goroutine no quede bloqueada eternamente en un I/O.
  • Ecosistema Go & Estándares (net/http, context, pgx, error handling)
    🏭 Caso de Uso Práctico en Producción
    Microservicio HTTP con cancelación en cascada. Si un cliente aborta la llamada HTTP desde la app móvil, el context.Context cancela de inmediato la consulta SQL en ejecución en PostgreSQL (driver pgx) y la petición a Redis, liberando conexiones del pool al instante.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Estructuro proyectos bajo la convención estándar (cmd/ para entradas, internal/ para lógica de dominio encapsulada). Para manejar errores utilizo wrapping idiomático con fmt.Errorf("...: %w", err), lo que permite evaluar errores específicos con errors.Is() o extraer tipos de error con errors.As() sin perder el stack trace."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Por qué usar pgx sobre database/sql tradicional? pgx soporta tipos nativos de Postgres (JSONB, Arrays), Binary Protocol directo (mayor velocidad) y pipelines de queries sin pasar por la capa de abstracción genérica de Go.
  • TypeScript & NestJS Empresarial (IoC, Guards, Interceptors)
    🏭 Caso de Uso Práctico en Producción
    Arquitectura backend SaaS multi-tenant donde los permisos (Guards RBAC) y el formateo de respuestas de auditoría (Interceptors) se aplican de forma declarativa mediante decoradores sin ensuciar los controladores.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "NestJS provee un contenedor IoC de inyección de dependencias robusto. Organizo por Módulos desacoplados. La ejecución del ciclo de vida del request sigue un orden estricto: Middleware -> Guards (para Auth/Roles) -> Interceptors (Pre-request) -> Pipes (validación DTO con class-validator) -> Handler -> Interceptors (Post-request) -> Exception Filters."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Cuál es el peligro de usar Scope.REQUEST en los providers de NestJS? Cada petición HTTP creará una nueva instancia de la clase, destruyendo el patrón Singleton por defecto y reduciendo drásticamente el rendimiento bajo alto tráfico. Usa Singleton siempre que sea posible.
  • Kafka, RabbitMQ & AWS SQS/SNS
    🏭 Caso de Uso Práctico en Producción
    Kafka: Ingesta de métricas y tracking GPS de repartidores en tiempo real (Uber/PedidosYa) o stream de órdenes de compra (MercadoLibre).
    RabbitMQ: Colas de tareas asincrónicas individuales (generación de facturas PDF, envío de correos).
    AWS SNS+SQS: Arquitectura Fan-Out serverless. Cuando se registra un usuario, SNS publica un evento y 3 colas SQS distintas lo procesan de manera independiente.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Kafka no es solo un message broker, es un distributed commit log ordenado por particiones donde el mensaje persiste en disco y los consumidores manejan su propio offset. RabbitMQ es un broker AMQP tradicional orientado al ciclo de vida del mensaje (se elimina tras el ACK del consumidor)."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Cómo garantizas orden de mensajes en Kafka? El orden solo se garantiza dentro de la misma partición. Para ordenar por usuario/orden, debes usar una Partition Key consistente (ej. user_id).
  • Patrones Distribuidos (Saga, Transactional Outbox, CQRS)
    🏭 Caso de Uso Práctico en Producción
    Saga Orchestration: Proceso de pago en e-commerce (Reservar Stock -> Cobrar Tarjeta -> Crear Envío). Si el cobro falla, el Orquestador ejecuta transacciones de compensación para liberar el stock previamente reservado.
    Outbox Pattern: Evitar la falla 'Dual Write' escribiendo el registro en la DB y la tabla `outbox` en la misma transacción SQL local.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "En arquitecturas de microservicios evitamos transacciones distribuidas 2PC por temas de bloqueo. Implementamos Sagas con transacciones de compensación. Para resolver la inconsistencia entre guardar en la DB y publicar en el Broker, aplicamos el Transactional Outbox Pattern combinado con CDC (Debezium) o un polling worker."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Por qué el consumidor DEBE ser idempotente? Porque en sistemas distribuidos la garantía de entrega es At-Least-Once (al menos una vez). Si la red falla durante el ACK, el mensaje se procesará dos veces. Debes usar una tabla de deduplicación con el message_id.
  • Servicios AWS (ECS Fargate vs EC2, Lambda, IAM, VPC)
    🏭 Caso de Uso Práctico en Producción
    Despliegue de microservicios Go en AWS ECS Fargate corriendo dentro de subredes privadas de una VPC, comunicándose con PostgreSQL RDS a través de Security Groups estrictos y asumiendo un IAM Role específico para leer secretos desde AWS Secrets Manager.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Prefiero ECS Fargate para microservicios persistentes de alto tráfico porque elimina la sobrecarga operativa de parchear y escalar nodos EC2. Aplico el principio de Least Privilege en IAM mediante Task Roles específicas para cada contenedor."
    ⚠️ Preguntas Trampa & Pitfalls
    • Diferencia entre Security Groups y NACLs en AWS: Security Groups son stateful (se aplican a nivel ENI/instancia); NACLs son stateless (se aplican a nivel de Subnet).
  • Kubernetes, API Gateways & Trazabilidad (OpenTelemetry/Jaeger)
    🏭 Caso de Uso Práctico en Producción
    Un usuario hace click en 'Comprar'. La petición entra por Kong API Gateway, valida el JWT y la reenvía a Kubernetes. OpenTelemetry inyecta un encabezado traceparent HTTP para seguir la traza completa a través de 5 microservicios en Jaeger UI, identificando si la latencia viene del servicio de inventario o de la base de datos.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "La observabilidad moderna se apoya en los 3 pilares: Métricas (Prometheus/Grafana), Logs estructurados (JSON a ELK/Datadog) y Trazas Distribuidas (OpenTelemetry + Jaeger). La trazabilidad contextualizada por TraceID y SpanID es imprescindible para hacer post-mortems en arquitecturas de microservicios."
  • Redis Avanzado (Rate Limiting, Redlock, Distributed Lock)
    🏭 Caso de Uso Práctico en Producción
    CyberMonday / Flash Sales: 100,000 usuarios intentan comprar los últimos 10 tickets. Usar un **Distributed Lock (Redlock)** o un script Lua en Redis previene que dos transacciones concurrentes vendan el mismo ticket (previene sobre-venta por race condition).
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Redis corre en un solo hilo de ejecución para operaciones de datos, lo que garantiza atomicidad nativa. Para patrones complejos como Rate Limiting o Distributed Locks utilizo Scripts Lua ejecutados directamente en Redis. Esto evita viajes de red adicionales y previene condiciones de carrera."
    ⚠️ Preguntas Trampa & Pitfalls
    • ¿Qué es el problema del Cache Stampede / Thundering Herd? Ocurre cuando una clave de caché de alto tráfico expira y miles de peticiones simultáneas golpean la base de datos a la vez. Se soluciona con Mutex de Caché o Refresh Probabilístico (Early Expiration).
  • PostgreSQL Avanzado (JSONB/GIN, Particionamiento) & NoSQL
    🏭 Caso de Uso Práctico en Producción
    Postgres JSONB + GIN: Almacenar metadatos dinámicos e hiper-personalizables de productos manteniendo la capacidad de indexar e indexar búsquedas internas.
    ClickHouse: Almacenamiento analítico columnar de logs masivos e historial de eventos para consultar miles de millones de filas en milisegundos.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Para datos semi-estructurados en Postgres utilizo `JSONB` indexado con un índice `GIN`, logrando rendimiento cercano a MongoDB sin perder las garantías ACID relacionales. En tablas masivas de auditoría con millones de registros aplico **Table Partitioning** por rango de fechas para acelerar queries y facilitar la purga de datos."
  • Arquitectura Hexagonal (Ports & Adapters) & DDD
    🏭 Caso de Uso Práctico en Producción
    Poder reemplazar PostgreSQL por MongoDB o migrar el transporte de HTTP REST a gRPC sin modificar una sola línea de la lógica del Dominio de Negocio, únicamente implementando una nueva clase o struct Adapter.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Arquitectura Hexagonal aísla las reglas de negocio en el núcleo. El Dominio define Ports (interfaces) para la entrada y salida. La infraestructura (HTTP, SQL, Kafka) son Adapters externos. Esto garantiza testabilidad unitaria total sin levantar bases de datos."
  • gRPC / Protocol Buffers & Contract-First
    🏭 Caso de Uso Práctico en Producción
    Comunicación interna de baja latencia entre microservicios backend en Go. Reduce el uso de ancho de banda hasta un 60% comparado con REST/JSON gracias al empaquetado binario Protobuf sobre HTTP/2.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "En comunicación inter-servicios adoptamos **Contract-First** definiendo archivos `.proto` o especificaciones OpenAPI antes de escribir código. gRPC utiliza tipos estrictos compilados y transporte HTTP/2 multiplexado."
  • Foundry (Forge, Cast, Anvil) vs Hardhat
    🏭 Caso de Uso Práctico en Producción
    Testing de contratos inteligentes DeFi en Solidity con Fuzz Testing (generación masiva de parámetros de entrada aleatorios) y Mainnet Forking para validar interacciones reales con Uniswap/Aave en segundos.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Foundry es el estándar moderno en Rust para el desarrollo EVM. Permite escribir tests directamente en Solidity en lugar de JS/TS, alcanzando una velocidad de ejecución hasta 10 veces mayor y ofreciendo Fuzzing nativo con `vm.assume()`."
  • Integración Backend <-> EVM (go-ethereum & Viem)
    🏭 Caso de Uso Práctico en Producción
    Servicio Backend Go (`go-ethereum`) suscrito a WebSockets de la red Ethereum para escuchar el evento `Transfer` de un contrato inteligente y acreditar el saldo en la base de datos relacional del usuario en tiempo real.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "Con `go-ethereum` utilizo `abigen` para generar bindings Go fuertemente tipados a partir del ABI del contrato. Firmo transacciones de forma segura offline con llaves ECDSA y utilizo **The Graph (Subgraphs)** para consultar datos históricos mediante GraphQL."
  • Seguridad Smart Contracts & ERC-4337 (Account Abstraction)
    🏭 Caso de Uso Práctico en Producción
    Reentrancy Protection: Proteger funciones de retiro en Smart Contracts usando `ReentrancyGuard` o Checks-Effects-Interactions.
    ERC-4337: Permitir transacciones Gasless (pagadas por sponsor/Paymaster) y login social en dApps.
    🎙️ Cómo Explicarlo en la Entrevista Senior
    "El ataque de Reentrancy ocurre cuando un contrato malicioso vuelve a llamar a la función de retiro antes de que el estado interno actualice el balance. Se soluciona aplicando el patrón Checks-Effects-Interactions. En UX Web3, **ERC-4337** introduce Account Abstraction permitiendo UserOperations procesadas por Bundlers sin alterar la capa de consenso EVM."

GO CONCURRENCY
¿Cuál es la diferencia entre un Buffered Channel y un Unbuffered Channel en Go?
Un Unbuffered Channel requiere que tanto el sender como el receiver estén listos simultáneamente (bloqueante/sincrónico).

Un Buffered Channel permite enviar mensajes sin bloquear hasta llenar la capacidad especificada del buffer.

NESTJS Custom Auth Guard & Reflector 
import { Injectable, CanActivate, ExecutionContext } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<string[]>('roles', context.getHandler());
    if (!requiredRoles) return true;
    const { user } = context.switchToHttp().getRequest();
    return requiredRoles.some((role) => user.roles?.includes(role));
  }
}
